# 功能评审与后续路线图

初评日期：2026-10-01；实现状态复核：2026-10-05。复核依据为当前 `feature/add_tmux_session_task` 源码、测试和文档；「已实现」只指当前分支具备代码与本地验证，不代表生产服务已更新。

**状态标记**：✅ 当前分支已实现；◐ 部分实现，阶段验收尚未完成；□ 尚未实现或未验证。首批五项的交付内容、使用边界和证据见 [第一阶段交付清单](phase-one-checklist.md)。第 3 节保留初评时的问题描述，紧随其后的「复核」说明当前变化。远端 CI、生产发布和真实手机验收没有本次核对证据。

## 1. 产品方向

项目已经从「飞书触发 Codex 的桥接器」发展成个人远程开发工作台：飞书负责派单和通知，Web 负责查看、接续和介入，tmux 负责操作已有终端会话。

下一阶段应围绕一个完整使用过程收敛：**手机提交 → 确认接收 → 看懂进展 → 处理异常 → 继续同一任务 → 检查结果 → 找回历史**。优先解决重复提交、上下文中断、状态分散和恢复困难，再增加新的入口与自动化。

规划假设：继续服务于个人、多项目、手机高频访问的场景。这里不假定要发展成多人 SaaS，也不把所有执行路径改成同一个后端。

## 3. 初评短板及当前复核

### R1：发送回执与可恢复提交之间还有缺口（P0）

- Web 创建任务每次在 `Dispatcher.submitWebTask()` 中生成新的 UUID；提交 API 没有客户端幂等键。服务已接收但响应丢失后，用户再次提交可能创建第二个任务。见 [dispatcher.ts](../src/dispatcher.ts) 和 [web.ts](../src/web.ts) 的 `createTask()`。
- 历史续聊的 `liveRuns`、`latestRunByThread`、`stagedAttachments` 都是内存 Map。进程重启后，Bridge 无法直接按旧 run ID 继续提供本轮更新、附件映射或中断控制。Codex 自身历史仍可能存在；不能把此问题描述成所有聊天记录丢失。见 [codex-history.ts](../src/codex-history.ts)。
- tmux 客户端发送生成新 `requestId`，10 秒未收到回执就报错；服务端用该 ID 回传结果，未见去重记录。同一次用户操作重试时可能再次输入。见 [TmuxDashboard.tsx](../web/src/TmuxDashboard.tsx) 的 `sendMessage()` 和 [tmux-dashboard-api.ts](../src/tmux-dashboard-api.ts) 的消息处理。

最小补齐：Web/历史提交持久化请求键与接收结果，重试返回原 task/run；同键不同内容返回冲突。历史只持久化 Bridge 自己的运行元数据，通过官方接口核对 Codex 状态。tmux 增加有界请求记录与「发送结果未知」状态；写入终端与写数据库无法组成原子事务，崩溃窗口内不自动重放，也不承诺恰好一次执行。

**复核：◐** Web 创建、原任务追加和 Codex History 续聊均已保存幂等回执；同键重放返回原任务/run，异内容冲突。历史续聊只把 Bridge 的最小运行元数据写入 SQLite，不保存提示词和流式正文；重启前仍活动的 run 标记为 `interrupted`，查询时通过官方 `thread/read` 只读核对，不自动重发。tmux 已拦截近期重复内容；超时的持久化 `sending` 记录在只读查询中显示“送达结果未知”，数据库重开专项通过，进程级故障注入仍待验证。[证据：Web 提交](../src/dispatcher.ts)、[回执表](../src/db.ts)、[tmux 查询/提交](../src/db.ts)、[历史服务](../src/codex-history.ts)。

### R2：任务分散在不同入口，首页没有覆盖主要派单链路（P1）

[App.tsx](../web/src/App.tsx) 调用 `/api/tasks`，后者查询 `tasks/runs`；另有 `/api/aamp/tasks` 查询接口，但当前首页没有消费它。Web 路由中未见对应 Direct `bridge_tasks` 的列表与详情入口。飞书派出的 Direct 任务不能直接在现有 Task Desk 列表里统一查看和操作。

最小补齐：增加只读聚合视图，稳定键使用 `source + sourceId`，展示来源、项目、状态、最后进展、更新时间和可用操作。保留各链路原始状态与业务规则；取消、续问、重试仍调用所属服务，不合并数据库状态机。tmux 作为独立 session 入口，只有明确记录关联时才链接，不能靠名称或目录猜测其对应任务。

**复核：◐** `/api/task-panel` 和首页现汇总 Bridge Task Desk、Direct 与 AAMP；稳定键、来源筛选、各自详情深链和「待处理」筛选已接入。AAMP 在面板中保持只读；Bridge/Direct 的追加仍走各自状态机。跨来源本地 HTTP 回归已通过，真实飞书任务及手机浏览器尚未验收。[证据：聚合查询](../src/db.ts)、[任务面板](../web/src/App.tsx)、[Web 路由](../src/web.ts)。

### R3：Web 任务尚未形成持续迭代与验收闭环（P1）

[App.tsx](../web/src/App.tsx) 明确显示「看板任务后续内容请新建任务提交」；反馈表单只对旧 `origin=feishu` 任务开放。已有最终响应和运行事件展示，但最终响应仍以 `pre` 为主，文件浏览是项目当前目录，并非任务产物快照。

最小补齐：Web 原任务追加说明、同线程续问、失败后的显式重试；新轮次独立记录输入和结果。结果页提供 Markdown、产物链接、运行证据及人工验收状态。把「执行完成」与「用户验收通过」分开，保留原执行状态，不强改现有状态枚举。文件或 diff 必须标明采集时间/基线；共享工作目录的所有改动不能自动归因到某个任务。

**复核：◐** Web 同 thread 续问、逐轮 Markdown 结果、失败/取消后的显式幂等重试、按 run 保存的人工验收记录已实现。详情展示每轮 Git 工作区执行前后采集时间、HEAD、变更路径和有界 SHA-256/大小指纹；指纹保存在 run 快照中，文件内容不保存。页面可以打开当前文件，并明确标注当前内容可能不同于采集时、共享目录变化无法归因。越界、符号链接、不可读和超限文件会标记跳过，采集失败不阻断执行。不可变文件内容或 diff 仍未提供，真实手机闭环也未完成。[证据：续问调度](../src/dispatcher.ts)、[任务详情](../web/src/TaskDetailPage.tsx)、[快照采集](../src/run-artifacts.ts)。

### R4：移动端草稿与配置读取行为不一致（P1）

- tmux 已有 [tmux-draft-store.ts](../web/src/tmux-draft-store.ts)，文字与附件分别使用本地存储和 IndexedDB。
- Task Desk 新任务以及 [CodexHistoryMessageComposer.tsx](../web/src/CodexHistoryMessageComposer.tsx) 的输入主要保存在 React state，未见等价的持久草稿机制。
- [api.ts](../web/src/api.ts) 的 `fetchShortcutConfig()` 仍直接请求 API，快捷键管理写操作没有共享缓存失效逻辑。

最小补齐：Task Desk 按项目、历史续聊按 home/thread 保存草稿，隔离设备服务实例与会话身份；提交成功后清除，失败保留，退出/撤销配对时明确本地数据处理。快捷键读取遵循「缓存 → API → 默认」，所有配置变更统一失效；显式禁用全部快捷键必须保留，不能被默认配置重新启用。跨标签页同步，跨设备通过轻量版本信号或事件刷新。

**复核：◐** Task Desk 新建文字草稿按项目保存，Codex History 文字和附件草稿按 home/thread 保存；两者现用服务安装实例与当前设备会话派生的作用域隔离，撤销当前设备时清除该作用域。Task Desk 暂存附件只提示重新选择。快捷键采用缓存、API、默认值的读取顺序，写入后本机失效、跨标签页同步，活动页面每 30 秒检查服务端配置版本以发现其他设备的改动。持久化草稿依赖浏览器本地存储；真实弱网和多设备交互尚未验收。[证据：草稿](../web/src/task-create-draft-store.ts)、[历史草稿](../web/src/codex-history-draft-store.ts)、[快捷键缓存](../web/src/shortcut-config-cache.ts)。

### R5：程序回滚已具备，数据恢复尚未闭环（P1）

[scripts/update-portable-release.mjs](../scripts/update-portable-release.mjs) 会切换 `current` 并在失败时恢复程序版本；这不等于恢复已迁移的 SQLite 数据。当前源码、脚本和 CLI 中未找到面向 Bridge 主库的完整备份/恢复命令与恢复演练。

已有 Web 暂存附件清理和历史回合过期清理，不能称为「完全没有清理」。但这些策略分散，历史清理依赖进程内计时器；tmux 输入附件写入临时目录，未见统一容量、引用和保留期管理。

最小补齐：对 Bridge 主库使用一致性快照方式备份，记录 schema/程序版本及附件清单，提供校验、备份列表和恢复到新目录的演练；升级前验证数据库向后兼容性。附加存储统计、清理预览、保留策略，保护运行中和已关联文件。不要在运行中的 WAL 数据库上只复制主 `.db` 文件；不得将 Codex 账户状态库纳入自行解析/修复流程。恢复正式数据需要显式操作，不能在程序回滚时悄悄覆盖新任务。

**复核：◐** `backup create/list/inspect/verify/restore/check-upgrade` 已有 CLI 和系统管理页面入口。清单 v2 从 `tmux_session_actions` 的任务提交内容提取受控 UUID 附件引用，并在恢复时重写路径；为旧临时目录迁移过的引用，会按 UUID 在 Bridge 管理的 tmux 附件目录中查找仍存在的副本。只读核对正式库发现 47 个唯一 tmux 附件引用、约 14.1 MiB，其中 7 条仍记录旧临时路径；v2 在私有临时目录完成备份、哈希校验、升级兼容检查和恢复，47 个恢复路径均有文件、恢复库外键检查无违例，临时目录已清理。截图中的备份是 v1，格式不记录 tmux 附件，因此仍显示 0；旧 v1 文件不会被改写，若恢复时发现缺少 tmux 附件引用则拒绝不完整恢复。`database.sha256` 和附件 `sha256` 是各自文件内容的 SHA-256；清单 JSON 自身没有哈希。列表只读元数据，执行校验、升级检查或恢复时才重算。`schemaFingerprint` 是 SQLite schema 定义指纹。定期备份调度和 tmux 附件保留/清理策略仍待完成。[证据：备份实现](../src/bridge-backup.ts)、[备份测试](../tests/bridge-backup.test.ts)、[运行状态](../src/system-health.ts)。

### R6：手机上看得到任务，但难以判断系统为何不工作（P1）

当前 `/healthz` 仅返回 `{ ok: true }`，证明 HTTP 处理器存活。CLI 已有 `codex:doctor/status/outbox/retry/recover`，这是一套可复用的基础，而 Web 系统管理尚无对应运行健康视图。见 [web.ts](../src/web.ts) 和 [codex-cli.ts](../src/codex-cli.ts)。

最小补齐：增加授权访问的运行状态页，展示运行模式/版本、依赖可用性、队列与最长等待、租约状态、outbox 积压和最近错误。区分 Codex 执行失败与飞书结果投递失败；重发卡片不能再次执行任务。公共 liveness 保持简洁，配置和敏感状态留在授权接口。首版状态查询不能顺带发消息、切换运行模式或重启服务。

**复核：◐** 授权的 `/api/system/health` 和运行状态页已展示模式/版本、已配置 Codex CLI 可执行性、三来源状态计数与当前排队记录的最早更新时间、Direct 租约、飞书 outbox 和最近错误；存储统计包含 Web/Direct/History/AAMP 及 tmux 受控目录中的引用/未引用文件，Web 暂存附件有只读过期预览。tmux 文件扫描有界、symlink 排除，页面只统计不删除。飞书网络明确标为未主动探测，公共 `/healthz` 仍仅为存活探针。尚未用生产故障、真实飞书投递及手机页面验证诊断结论。[证据：健康快照](../src/system-health.ts)、[页面](../web/src/SystemHealth.tsx)。

### R7：自动化验证晚于日常迭代，现有测试已有契约漂移（P0）

仓库有较多服务端和辅助逻辑测试，并非没有测试。但是 [release.yml](../.github/workflows/release.yml) 仅在 `v*` tag 推送时执行，未见 PR/普通分支检查工作流；包依赖和测试目录中未见浏览器端到端测试套件。

本次验证发现 [codex-history.test.ts](../tests/codex-history.test.ts) 要求回合结束后附件目录立即为空，而服务现在保留附件供回看，并在过期/淘汰时清理。这是确认存在的行为与测试契约不一致，不能简单以删除断言处理。

最小补齐：先明确附件生命周期，覆盖回看、到期、淘汰、重启遗留和运行中保护。增加 PR 类型检查与测试，再建立配对、任务提交、历史续聊、tmux 重连、文件预览/上传这五条浏览器冒烟链路。移动模拟不替代真实手机软键盘、长按复制与滚动验收。

**复核：◐** 附件生命周期测试已修正并覆盖上述主要边界；[CI 工作流](../.github/workflows/ci.yml) 已配置 PR/分支 push 的测试和构建；[浏览器冒烟清单](browser-smoke-checklist.md) 已列出步骤。隔离浏览器仅执行过配对/登出、Web 提交及 Direct 查看相关检查；历史续聊、tmux 重连和文件页浏览器检查、真机验收及远端 CI 结果尚无证据。

### R8：历史规模增长后会拖慢，维护成本也在上升（P2）

`CodexHistoryService.queryHome()` 遍历返回页，`listThreads()` 合并排序后再做分页；最多扫描 10,000 条。限制能防止无界扫描，但列表翻页仍可能重复拉取大量历史。当前没有据此测得的生产性能结论，应先采样再优化。

`src/web.ts`、`src/db.ts`、`src/feishu-sqlite-codex.ts` 以及几个前端页面已经承载大量职责。优先随功能拆出任务查询、提交、文件访问、维护服务与共享 composer 逻辑，保留鉴权边界；不安排一次性重写。

文档也需要收敛：README 开头的旧轮询/Dispatcher 说明容易与后文 Web Task Desk 混淆，CHANGELOG 对历史页仍主要描述为只读，旧 tmux 执行计划已经标注取消。增加「入口 → 执行器 → 状态来源 → 支持动作」能力表，避免照历史方案开发。

**复核：◐** [README 能力表](../README.md) 已补充；Codex History 列表已有按 home/filter 的缓存，快捷键缓存失效与跨设备版本刷新已接入。仍未以真实规模记录请求数、首屏耗时与内存，也未完成模块拆分。

## 4. 分阶段路线图

以交付门槛推进，不把以下阶段绑定到尚未发布的版本号。工作量 S 约 1–2 人日、M 约 3–5 人日、L 约 6–10 人日，仅为粗估；不含外部协议变化和发布等待，完成方案细化后重新估算。

| 阶段 | 当前标记与已交付 | 剩余验收条件 | 原粗估 / 依赖 |
| --- | --- | --- | --- |

## 5. 验收指标与暂缓范围

优先记录以下指标，先建立基线，再设服务时延目标：

- 自动化故障场景下，重复请求只创建一个 Web task/历史 run；未知 tmux 投递不会自动再次输入。
- 浏览器刷新、网络断开、服务重启分别有独立恢复测试，不能用其中一种替代另外两种。
- 在统一任务视图中，每条记录都有可核实的来源与详情；执行失败和通知失败可区分。
- 定期从备份恢复到独立目录，校验关键记录数量、关联完整性与附件可用性。
- 对代表性的大量历史和长会话采集首屏耗时、列表查询耗时、请求数量、内存以及手机滚动表现；未实测前不承诺延迟数字。

暂缓：增加另一套执行引擎、恢复旧 verifier/tmux 任务后端、多用户角色体系、无前置验证的自动并行改代码、跨账号自动切换、先做复杂全文/向量检索、只为离线入口增加一整套 PWA。后续若真实使用需求改变，再单独评估。
